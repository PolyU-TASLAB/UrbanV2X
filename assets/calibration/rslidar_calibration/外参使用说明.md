# 路侧 LiDAR 外参使用说明

这份说明定义公开外参的全部坐标约定和使用方法。公开文件不依赖点云地图，也不要求使用方知道私有地图的原点。

## 1. 文件和字段

每个站点有一个合并文件和每台雷达的独立文件：

- `ekeo/poses.yaml`、`ekeo/poses.csv`
- `hkstp/poses.yaml`、`hkstp/poses.csv`
- `<sensor_id>_lla_attitude.yaml`
- `<sensor_id>_lla_attitude.json`

每个独立 YAML/JSON 记录包含以下内容：

| 字段 | 含义 |
|---|---|
| `position_lla_wgs84` | 雷达原点的 WGS84 大地坐标；纬度、经度单位为度，高度为 WGS84 椭球高（米） |
| `enu_anchor_lla_wgs84` | 该站点公开 ENU 坐标系的原点。当前 EK 使用 `ekeo_1`，HKSTP 使用 `hkstp_2a` |
| `position_enu_m` | 雷达原点相对于该 ENU 原点的位置，顺序为 East、North、Up，单位米 |
| `T_Rj` | 从雷达坐标系 R 到站点 ENU 坐标系的位姿 |
| `T_Rj.rotation_matrix_enu_sensor` | 3×3 旋转矩阵，传感器坐标中的向量乘此矩阵后得到 ENU 坐标中的向量 |
| `T_Rj.translation_enu_m` | 与 `position_enu_m` 相同，表示雷达原点在 ENU 中的位置 |
| `T_Rj.quaternion_wxyz` | 同一个旋转的四元数，顺序是 `w, x, y, z` |
| `attitude.rpy_deg_xyz` | 从同一个矩阵提取的 roll、pitch、yaw，单位为度 |
| `attitude.heading_sensor_plus_x_deg` | 雷达 `+X` 轴在水平面的方位角 |
| `quality` | 点云重合诊断值，不是测量真值精度证明 |

## 2. 坐标系定义

ENU 原点是 `enu_anchor_lla_wgs84` 对应的地球位置。三个轴为：

- **East**：当地水平面向东；
- **North**：当地水平面向北；
- **Up**：椭球法线方向向上。

ENU 是右手坐标系。经纬度使用 WGS84 椭球，`altitude_m` 不是海拔正高；如果系统使用正高，需要另外应用大地水准面模型转换。

在系统代码中，世界坐标记作 `W`，这里的 `W` 就是以 `anc_ecef` 为原点的全局 ENU。`anc_ecef` 是
一个 WGS84 ECEF 三维点，通常由车辆起始位置或部署方选定的 GNSS 锚点得到。把任意 WGS84 位置先转成
ECEF 后，世界坐标按下面的关系计算：

```text
p_W = R_enu_ecef · (p_ECEF - anc_ecef)
```

`R_enu_ecef` 的三行分别是 East、North、Up 轴在 ECEF 中的单位向量。公开文件为了不暴露私有地图原点，
采用 `enu_anchor_lla_wgs84` 表示同一个锚点；需要接入已有系统时，可以用该 LLA 生成 `anc_ecef`，或者用
`scripts/reanchor_public_enu.py` 直接换成部署方的锚点。LLA 是跨系统传递位置的主值，ENU 只是在某个明确
锚点下的局部米制表达。

雷达坐标系使用驱动发布点云的坐标轴。设雷达坐标中的点为
`p_R = [x_R, y_R, z_R]^T`，则公开位姿的定义是：

```text
p_ENU = R_ENU_sensor · p_R + t_ENU
```

其中：

```text
T_Rj = [ R_ENU_sensor  t_ENU ]
       [      0 0 0       1  ]
```

`R_ENU_sensor` 的列向量分别是雷达 `+X`、`+Y`、`+Z` 轴在 ENU 中的方向。雷达原点的 ENU 坐标就是 `t_ENU`。

如果需要反向变换，旋转矩阵是正交矩阵，因此：

```text
p_R = R_ENU_sensorᵀ · (p_ENU - t_ENU)
```

### 与车端 LiDAR、IMU 和路侧前端的关系

系统中车辆 IMU/body 坐标系记为 `B`，车端 LiDAR 坐标系记为 `L`。车辆状态
`(t_v, q_v)` 表示 body 原点和 body 姿态在世界 ENU 中的位置与朝向；车端 LiDAR 的安装参数是
配置中的 `ql2b_*`、`tl2b_*`（代码变量 `q_lb`、`t_lb`）。沿用程序使用的方向，车端点 `p_L` 变到世界的
完整公式是：

```text
p_W = q_v · ( q_lb⁻¹ · (p_L - t_lb) ) + t_v
```

这里的逆变换和减法必须按现有配置的父子坐标方向执行，不能把 `ql2b/tl2b` 当成路侧外参直接替换。
公开文件只描述固定路侧 LiDAR `R` 到世界 ENU 的关系：

```text
n_W = q_r · n_R
c_W = q_r · c_R + t_r
```

其中 `n_R`、`c_R` 是路侧点或平面法向，`q_r`、`t_r` 正是公开 `T_Rj` 中的旋转和平移。路侧点云与车端
点云建立共视约束时，先分别按上面两条公式变到同一个 `W/ENU`，再做点面或地图约束；不能把路侧
`T_Rj` 当作车端 `L→B` 安装外参。

## 3. 姿态角和四元数

文件中的四元数统一为 `quaternion_wxyz = [w, x, y, z]`。ROS 消息的字段顺序是 `x, y, z, w`，写入 ROS 时必须重排：

```text
file: [w, x, y, z]
ROS : orientation.x = q[1]
      orientation.y = q[2]
      orientation.z = q[3]
      orientation.w = q[0]
```

`rpy_deg_xyz = [roll, pitch, yaw]` 使用常见的 XYZ 分解，矩阵重建关系为：

```text
R = Rz(yaw) · Ry(pitch) · Rx(roll)
```

`heading_sensor_plus_x_deg` 是雷达 `+X` 轴的水平投影方位角：从 East 轴逆时针转向 North 轴，范围为 `[-180, 180)`。它不是车辆车头航向，也不是雷达 `+Y` 轴的方位角。

每条记录还提供 `attitude.local_tangent_enu_at_sensor`。它把同一个姿态改写到雷达所在位置的局部切平面 ENU；跨越较大范围时，若系统每个位置都使用自己的局部 ENU，可使用这一字段。需要把多台雷达放在同一个坐标系中时，应使用主 `attitude` 和 `T_Rj`。

## 4. 在程序中使用

读取 YAML 后，点云变换的核心代码等价于：

```python
import numpy as np

R = np.asarray(record['T_Rj']['rotation_matrix_enu_sensor'], dtype=float)
t = np.asarray(record['T_Rj']['translation_enu_m'], dtype=float)
p_enu = (R @ p_sensor.T).T + t
```

如果只需要雷达的位置和朝向，可以直接使用：

```python
lla = record['position_lla_wgs84']
q_wxyz = record['attitude']['quaternion_wxyz']
heading_deg = record['attitude']['heading_sensor_plus_x_deg']
```

如果系统已经有自己的 GNSS ENU 原点，可以把公开记录重新表达在新的原点下。工具只读取公开 YAML，不读取地图或旧的地图外参：

```bash
python3 scripts/reanchor_public_enu.py \
  public_calibration/ekeo/poses.yaml \
  --anchor-lat 22.3300000000 \
  --anchor-lon 114.2000000000 \
  --anchor-alt 5.000 \
  --output /tmp/ekeo_poses_in_deployment_enu.yaml
```

重新锚定只会改变 `position_enu_m` 和 ENU 表达下的旋转矩阵/四元数；每台雷达的 LLA 不变。部署时建议把 GNSS 系统实际使用的 `anc_ecef` 或等价 LLA 作为锚点，而不是长期使用当前的首台雷达作为锚点。

## 5. ROS TF 用法

如果系统的父坐标系就是该站点 ENU，可以发布静态 TF。文件使用 `wxyz`，而 `static_transform_publisher` 的命令行参数使用 `qx qy qz qw`：

```bash
rosrun tf static_transform_publisher \
  EAST NORTH UP \
  qx qy qz qw \
  enu roadside_lidar 100
```

实际填写时：

- `EAST NORTH UP` 来自 `T_Rj.translation_enu_m`；
- `qx qy qz qw` 来自 `T_Rj.quaternion_wxyz` 的第 2、3、4、1 个元素；
- `enu` 必须明确对应 `enu_anchor_lla_wgs84`；
- `roadside_lidar` 应与点云驱动的 `frame_id` 匹配。

如果使用 Python/C++ 发布 `geometry_msgs/TransformStamped`，则直接将 `T_Rj` 的平移写入 `transform.translation`，并按 ROS 的 `x,y,z,w` 字段写入四元数。

## 6. 这个文件不能被当成什么

`T_Rj` 是“路侧 LiDAR 原点和朝向在 ENU 中的位姿”，不是：

1. 私有 GLIO 地图坐标中的 `T_map_sensor`；
2. 车端 body/IMU 到 LiDAR 的安装外参；
3. 车辆车头航向；
4. 点云地图的精度证明。

如果需要车辆 body 与路侧 LiDAR 之间的安装关系，应另行定义 `T_body_sensor` 或 `T_sensor_body`，并明确父子坐标系方向。公开包中的 `median_nn_m` 和 `fraction_nn_under_0p3m` 只用于判断地图/点云重合情况。

## 7. 当前结果的私有和公开边界

旧的 `T_map_sensor`、地图原点、地图点云和私有运行目录保存在：

```text
calibration_outputs/archive_map_frame_20260922/
```

公开发布时只需要：

```text
public_calibration/
```

其中不包含 `T_map_sensor`、地图路径或点云路径。

## 8. 发布前检查

在复制公开目录或重新运行导出脚本后，在工作区根目录执行：

```bash
python3 scripts/validate_public_calibration.py
```

检查内容包括：每台雷达的 YAML、JSON 和合并文件是否一致；旋转矩阵是否正交且行列式为 `+1`；四元数
是否归一化；`T_Rj` 平移是否等于 `position_enu_m`；公开记录是否意外带入私有地图路径、地图坐标字段
或未声明的发布备注字段。该检查不读取点云地图，也不依赖 `T_map_sensor`。
